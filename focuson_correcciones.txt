Error 1 — Notificaciones repetitivas no 
implementadas  
El problema  
El campo repeat_minutes existe en la tabla tasks y aparece en el formulario de creación de 
tareas con opciones de 30 min, 1h, 2h y 3h. Sin embargo, la función 
scheduleTaskNotification en lib /notifications.ts usa exclusivamente un trigger de tipo DATE, 
que dispara la notificación una única vez en la fecha y hora indicadas. Una vez disparada, si 
el usuario no la ve o no completa la tarea, no vuelve a aparecer.  
El objetivo declarado de la app es  precisamente el opuesto: los recordatorios deben 
repetirse hasta que la tarea se complete. Tal como está, el núcleo del producto no funciona.  
 
Impacto  
Un usuario que no vea la notificación inicial (pantalla bloqueada, modo no molestar, distracción) no 
recibe ningún aviso adicional. La tarea queda olvidada. Esto contradice directamente el propósito de 
la app.

Página 3 de 13 La solución  
Hay que separar la lógica en dos notificaciones para cada tarea que tenga repeat_minutes > 
0: una notificación principal a la hora programada, y una segunda notificación de 
seguimiento con un trigger de intervalo en segundos que se repita indefinidamente. Al 
marcar la tarea como completada, ambas notificaciones deben cancelarse usando sus IDs 
respectivos. Para ello hay que guardar los dos IDs en la base de datos.

Error 2 — Toggle de notificaciones roto al reactivar  
El problema  
En la pantalla de Settings hay un toggle para activar o desactivar las notificaciones. La 
documentación reconoce explícitamente el fallo: al desactivar se cancelan todas las 
notificaciones existentes, pero al volver a activar no se reprograman. El usuario queda sin 
recordatorios de forma silenciosa, sin ningún mensaje de advertencia.  
 
Por qué es crítico  
Un usuario que accidentalmente desactive el toggle y lo vuelva a activar creerá que sus 
notificaciones están funcionando cuando en realidad se han perdido t odas. Es un fallo silencioso, el 
peor tipo.

Error 3 — La racha se rompe al usar  resetDay()  
El problema  
La función calcStreak() calcula la racha buscando días consecutivos en el campo 
completed_at de las tareas. Cuando el usuario llama a resetDay(), la función 
toggleTaskComplete se invoca con completed = false para todas las tareas, borrando el FocusOn — Plan de corrección técnica  
Página 7 de 13 valor de comp leted_at. Resultado: el historial de ese día desaparece completamente y la 
racha se rompe, aunque el usuario sí había completado tareas.  
El mismo problema ocurre si el usuario borra tareas completadas manualmente: el historial 
se pierde. Para una app basad a en la motivación por rachas, esto es especialmente dañino.  
 
La solución — tabla daily_log  
La racha no debe depender de los datos en tiempo real de la tabla tasks. Necesita una tabla 
de solo escritura que registre los logros del día de forma permanente, i ndependiente de 
resets o borrados.

export function updateDailyLog(date: string): void {  
  const rows = db.getAllSync<{ total: number; completed: number }>(  
    `SELECT  
       COUNT(*) as total,  
       SUM(CASE WHEN is_completed = 1 THEN 1 ELSE 0 END) as completed  
     FROM tasks  
     WHERE scheduled_date = ?`,  
    [date]  
  ); 
  const { total, completed } = rows[0] ?? { total: 0, completed: 0 };  
  db.runSync(  
    `INSERT INTO daily_log (date, completed_count, total_count)  
     VALUES (?, ?, ?)  
     ON CONFLICT(date) DO UPDATE SET  
       completed_count = excluded.completed_count,  
       total_count = excluded.total_count`,  
    [date, completed, total]  
  ); 
} 
 
export function getDailyLog(): { date: string; completed_count: number; 
total_count: number }[] {  
  return db.getAllSync(`SELECT * FROM daily_log ORDER BY date DESC`);  
}

Paso 4 — Reescribir calcStreak usando daily_log  
Fichero:  
La lógica de la racha ahora lee de daily_log en lugar de buscar en completed_at de tasks. 
Un día cuenta para la racha si completed_count > 0.  
 
function calcStreak(log: DailyLogEntry[]): number {  
  let streak = 0;  
  const today = new Date();  
  for (let i = 0; i < 365; i++) {  
    const d = new Date(today);  
    d.setDate(d.getDate() - i); 
    const iso = d.toISOString().split("T")[0];  
    const entry = log.find(l => l.date === iso);  
    if (entry &&  entry.completed_count > 0) {  
      streak++;  
    } else if (i > 0) {  
      // Permitir que el día de hoy no tenga tareas aún  
      break;  
    } 
  } 
  return streak;  
}

Error 4 — Historial de estadísticas se pierde al 
borrar  
El problema  
Los porcentajes de completado y el conteo total en la pantalla de Stats se calculan sobre el 
array tasks en memoria, que se carga con getAllTasks() o getTasksByDate(). Si el usuario 
usa la opción "Eliminar todo" de Settings, o borra tareas completadas para  limpiar la lista, 
todos esos datos desaparecen y las estadísticas vuelven a cero.  
 
Consecuencia  
Completar un ciclo de 30 días y luego borrar las tareas antiguas significa perder toda evidencia del 
progreso. Para un usuario motivado por los datos y las rachas, esto puede ser desmotivador.  
 
La solución  
Este error queda resuelto como efecto secundario de la corrección del Error 3. La tabla 
daily_log actúa como historial permanente porque:  
 
• updateDailyLog hace un INSERT ... ON CONFLICT DO UPDATE, nunca borra filas.  
• purgeAll() en el store borra tasks pero no debe borrar daily_log.  
• Las estadísticas históricas leen de daily_log, no de tasks.
